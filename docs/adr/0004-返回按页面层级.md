# ADR 0004：返回按页面层级，不按浏览器历史

- 状态：已采纳（2026-10-30；Web 侧修订，v1.0.19 壳无需升级）
- 影响面：`js/ui/back.js` 的 `zpResolveBack`、`pages/data.html` 的返回箭头、所有页面的 `from=` 入口
- 相关：`AGENTS.md` 第 8 节第 1、12 条；ADR 0002（不提供草稿）、ADR 0003（返回键不依赖浏览器历史）

## 背景

同一日内两次修订。修订 F（ADR 0003 的前置结论）把「单根收口」推到极致：

> 业务区**任何**页面返回 → `/home`，不看 `from=`、不看 `date`、不看运单 `id`。

它解决的是真问题——首页按返回会退回内页（历史栈残留）。但代价在子页面上暴露出来：

| 路径 | 修订 F 的行为 | 用户感受 |
|---|---|---|
| 历史 → 运单详情 → 返回 | 跳到首页 | 刚看的日期没了，得重新翻日历 |
| 派单 → 数据资料 → 返回 | 跳到首页 | 编辑中的线路上下文丢失 |
| 派单 → 线路申请 → 返回 | 跳到首页 | 同上 |
| 我的 → 隐私政策 → 返回 | 跳到首页 | 只是看个条款，却被打回起点 |

根因是把两件事混为一谈：

- **「返回不能退回已经离开的页面」**——这是历史栈残留问题，靠 `replace` + 占位只压根页解决；
- **「返回要回到上一层界面」**——这是导航语义问题，与历史栈无关。

修订 F 用「一律回根」去保证前者，顺手把后者也砍了。

## 决策

返回按**页面层级**走，层级显式声明在 `js/ui/back.js` 的 `zpPageDepth`：

| depth | 页面 | 返回目标 |
|---|---|---|
| 0 | `/home`、`/admin` | 两次返回退桌面 |
| 1 | `history`、`dispatch`、`account`、`today` | 区根（彼此不回跳） |
| 2 | `order_detail`、`data`、`route_apply`、`privacy`、`terms` | 来源父级（`from=` 白名单），无来源回区根 |

三条安全阀：

1. 目标是本站绝对路径（拒绝 `//evil`、外链、相对路径）；
2. 目标 depth **严格更小**（防 `from` 被手改成同级页导致 A↔B 死循环）；
   唯一例外是 detail⇄data 的编辑往返，在 `zpParentOf` 里显式 `allowSameDepth`；
3. 管理员区不产生业务路径目标（跨区防火墙不变）。

## 为什么不用浏览器历史

- 站内导航一律 `replace`（ADR 0003），栈里根本没有「上一页」；
- `history.back()` 会让「首页返回退回内页」的老问题复发（v1.0.18 前的实测序列
  `首页 → 首页 → 历史 → 首页`）；
- 层级是产品的确定结构，写明比推断可靠；`document.referrer` 与 `history.length`
  都不可靠（刷新、直链、多标签、PWA 冷启动各不相同）。

## `from=` 的边界

`from=` 只是**父级提示**，不是跳转指令。只认白名单键：

```
history → /pages/history?date=<原日期>
dispatch → /pages/dispatch
account → /pages/account
process → /home
home → /home
```

直接拿 `from` 拼路径是历史 bug 来源：`?from=admin` 曾能把业务页送进管理端。
新增来源必须进白名单，`tests/nav-return.test.mjs` 里有 `from=admin`、`from=constructor`、
`from=../admin`、`from=//evil.example/x` 四条对抗用例。

## 后果

- 子页面返回回到上一层，最多按三次到桌面（详情 → 列表 → 首页 → 桌面），路径可预期；
- `pages/data.html` 的编辑往返会带 `origin`，把详情页原本的来源透传下去，
  保证 `history → 详情 → 数据资料 → 返回 → 返回` 仍能回到历史；
- 未登记的新页面按 depth 1 处理：只往区根走，不会被编造层级；
- 浏览器里返回键仍是平台行为（ADR 0003），App 内不受影响。
