## 决策 1：错误响应按「域内错误 / 未预期异常」二分，而不是一律脱敏

**背景**：审计确认 `waybills/process.js` 把 `error.stack` 直接发给浏览器；`confirm.js`、
`base.js` 把 `e?.message` 原样回传。

**选择**：不做"全部改成通用文案"，而是引入 `functions/api/_errors.js` 二分：

| 类型 | 判定 | 对外 |
|---|---|---|
| 域内错误 | 带本系统错误码（`BASE_*` / `CONFIRM_*` / `OCR_*` …）且不含 `_INTERNAL_`/`_UNHANDLED_` | 透传中文业务提示（`detail` 截断 200 字） |
| 未预期异常 | 无 code / 兜底码 / 运行时原始异常 | 只给调用方通用文案，原文+stack 仅进 `console.error` |

**为什么不一律脱敏**：本项目大量业务失败本身就是"给用户看的中文提示"
（如"线路门店顺序必须从1开始连续排列"）。一刀切会让用户从"知道哪一步错了"
退化成"失败了，请重试"，这是体验倒退，也会逼前端写死文案。

**代价**：判定依赖错误码命名规范。若有人抛了带 `XXX_INTERNAL_YYY` 之外的
兜底码却没有中文文案，透传的还是兜底文案——这是安全的一侧，可接受。

**防回归**：`tests/error-response-discipline.test.mjs` 扫全 `functions/`：
除 `_errors.js` 外禁止出现 `.stack`；三个用户可见端点必须走 `clientMessage`
且必须 `logServerError`（脱敏不能把故障变成哑巴）。含投毒验证。

## 决策 2：不做 ACL「统一中间件化」，把判定继续留在 `_permissions.js` / `_waybill-acl.js`

**背景**：方案书 P0-1 假设"权限判定散落在各端点，缺统一入口"，原定阶段三重构为中间件。

**审计结论（阶段一）**：判定逻辑**已经**集中——29 个路由端点中 27 个引用共享模块，
两个"无引用"的是 `admin/bootstrap.js`（初始化入口，靠 `ADMIN_SETUP_KEY` + 原子 EVAL 自校验）
和 `admin/reset.js`（8 行 410 桩）。`dispatch.js`、`history-*`、`route-binding/unbind`
逐行复核后**未发现横向越权**。

**选择**：只做"函数级统一"（已存在），不做"请求级中间件"。理由：

1. 中间件只能做**粗粒度**判定（登录/角色），而本系统的关键判定是**数据级**
   （这张运单、这条线路归不归你），必然还要在 handler 内做——中间件化拿不到安全收益。
2. 29 个端点的签名改写是高风险重构（取消人审的前提下），收益是"看起来更整齐"。
3. 现状的可维护性由命名 + 测试保证，不需要额外抽象层。

**风险接受**：新增端点若忘记调用 `requireBusinessUser`/`currentUser`，没有任何机制拦截。
缓解：`AGENTS.md §7 安全纪律` 已写明"端点必须走 `_permissions.js`"，且
`tests/integration-admin-*` 系列对越权路径有反向断言。**这是记录在案的残余风险，不是已解决项。**

## 决策 3：`POST /api/dispatch` 的"任意用户可切任意启用线路"判定为设计意图，但登记为宽读取面

**事实**：任意业务用户 POST 一个 `routeId` 即可把自己的调度线路切到任一 `active` 线路，
随后可读该线路的门店资料（含客户电话/地址）与 24 个月历史。前端有选线界面，
`isSubstitute` 替班语义要求这一能力。

**选择**：保留（不做收紧）。**但这是当前系统最大的数据横向暴露面**：

- 单公司 4 人场景可接受（人人本来就要替班）；
- **一旦扩到多公司/多承包商，这是首要必须拆掉的假设**——届时需要引入
  "公司/组织"维度，把 `routes` 按组织隔离，`canUseRoute` 增加组织归属判定。

已写入 `AGENTS.md §8 已知架构决策`，避免后人误以为是漏洞"修"掉，或误以为安全。

## 决策 4：删掉 `android-build-check.yml`，保留 `android-ci.yml`

两份工作流触发条件完全相同（push/PR → main），步骤是严格包含关系
（`android-ci` 多依赖审计、模板漂移检查、模拟器冒烟）。每次提交跑两遍 debug 构建
= 双倍 CI 分钟数，属于零费用约束下的实际浪费。

`main` 分支保护的必过检查同步从 `build-check + android-debug-build` 收敛为
`android-debug-build`。回滚点：`backup/stage3-dedupe-android-ci-20261030`。

## 决策 5：`package-lock.json` 纳入版本控制，CI 用 `npm ci`

原 `.gitignore` 写着"仓库约定不跟踪锁文件"。代价是 CI 每次装"当时最新"的 devDeps
（构建不可重现）、`npm audit` 无锁文件可用（上一轮只能临时生成一份再审计）。

改为跟踪后：`npm ci` 严格按锁安装，`package.json` 与锁不一致直接失败；
依赖审计不再需要取巧。锁文件 60KB / 134 个包，diff 噪音可接受。

**注意**：这改变了原有约定，已在 `.gitignore` 与 `AGENTS.md` 留下反向说明，
防止后来者"按注释把锁文件加回去"。

## 决策 6：测试执行口径——`test:node` 并行、`test:serial` 保留为真值源

见 `AGENTS.md §4.5`。核心事实：原 97 段 `&&` 串行链**单点失败会静默跳过其后全部测试**，
2026-10-29 已实证（`home-bundle-fresh` 失败后 30+ 测试从未执行）。

现在 `test:node` = 并行执行器（全跑完再汇总），清单从 `test:serial` 反解，
`coverage` 仍走 `test:serial`（保持 c8 口径与棘轮数值不变，实测 82.94/66.15/84.77/82.94）。
