# 适配One · 2026-10-01 全面整改审计基线

## 目标

本轮不是推倒重来。保持现有核心业务架构、Redis 数据命名空间、线路权限模型、运单处理主链路和全局学习模型，在其上做一次“业务一致性 + Web 手机端 UI/UX + 前后端契约 + 真实回归”的系统性收口。

正式业务链路仍为：

上传运单 → 识别 → 提取 → 匹配 → 去重 → 规划 → 待定/新增确认 → 保存 → 今日运单 → 历史 → 基准库学习

## 一、当前审计结论

### P0：必须优先处理

1. **运单详情页面 DOM 与 JS 契约曾不一致**
   - JS 读取 `menuRoute`，页面缺少该节点。
   - “线路维护”曾指向不存在的 `/pages/route_edit.html`。
   - 本轮已在 main 修复：详情菜单节点补齐，并将入口统一到现有 `/pages/data.html`。

2. **线路申请状态前后端曾不一致**
   - 已批准后仍可继续提交申请。
   - 服务端现在以“同一用户 + 同一线路 + 同一岗位”的 approved/pending 状态作为硬约束。
   - 已绑定用户的前端申请控件同步禁用。
   - 后续仍需真实回归“批准 → 页面刷新 → 再申请 → 解除 → 再申请”。

3. **首页与正式产品文案曾混用旧交互**
   - 今日任务 / 当日线路等名称与当前确认方案不一致。
   - 首页已统一到：今日配送 / 上传运单 / 今日运单 / 历史查询。
   - 首页品牌副标题统一为：智能配送·一路领先。

### P1：核心闭环必须继续整改

4. **今日/历史数据模型需要与产品语义重新核对**
   - 当前历史接口以“线路 + 日期”索引单条 waybill。
   - 但正式唯一性规则包含“日期 + 线路 + 车辆 + 总重量 + 门店集合”，理论上同一天同线路可能存在不同业务运单。
   - 当前历史产品暂不扩展功能，但后续必须明确“一天一单”还是“一天多单”，并让 Redis 索引、历史 API、今日页面保持一致。

5. **历史保留周期与文档存在冲突**
   - 正式契约写明历史保留 100 天。
   - 当前 history API 的查询范围实现并非严格 100 天。
   - 历史页面目前按既定安排暂不继续扩展，先记录为 P1 数据契约整改项。

6. **`/api/routes` GET 存在读取时执行一致性修复的架构风险**
   - 当前为了修复线路岗位/用户绑定不一致，GET 读取流程会触发 reconciliation。
   - 长期应把修复动作移入管理员专用、显式的 reconciliation endpoint/helper。
   - 普通业务读取应保持只读，避免 GET 带副作用。

7. **运单处理仍需要真实阶段级回归**
   - 前端可以显示“识别 → 提取 → 匹配 → 去重 → 规划”，但最终可靠性必须以服务端各阶段耗时和诊断数据为准。
   - 不通过提高模糊匹配阈值、硬编码门店或客户端补规则解决真实回归问题。

## 二、Web 手机端 UI/UX 2.0 统一标准

### 视觉

- 背景：#05070A
- 主卡片：#18212B
- 输入/次级面：#11171D
- 分割线：#2A3540
- 主文字：#FFFFFF
- 次级文字：#B8C2CC
- 弱文字：#7F8A95
- 禁止业务蓝、玻璃拟态、渐变、强发光、3D 阴影。

### 布局

- 手机优先，桌面只是自然扩展。
- 内容最大宽度约 430–560px，避免手机页面横向拥挤。
- 使用 safe-area。
- 页面标题、返回、菜单的点击区域不得小于可用触控区域。
- 表单纵向排列，减少键盘弹出后的跳动。

### 交互

- 保存/确定右侧，取消左侧。
- 破坏性操作必须二次确认。
- 不再依赖浏览器原生 alert 作为正式业务反馈；逐步统一为应用内 toast / dialog / inline error。
- 加载、成功、失败、超时、取消必须对应明确 UI 状态。
- 禁止出现“按钮点击了但页面没有反馈”的状态。
- 页面刷新后状态必须可恢复，不依赖前端临时变量决定权限。

### 信息层级

首页只负责“今天要做什么”：
1. 当前配送线路
2. 今日配送状态
3. 上传运单
4. 今日运单
5. 历史查询

线路数据、线路申请、账号设置放入菜单。

运单详情只负责：
1. 日期 / 线路 / 车辆
2. 门店数 / 重量
3. 原始数 / 更正 / 合并 / 新增 / 待定
4. 配送顺序
5. 待定门店确认
6. 必要的分享/线路数据入口

## 三、移动 Web 技术原则

- 响应式布局，不建立独立的“手机域名”。
- CSS 优先使用现代布局能力和 safe-area。
- 图片必须考虑移动网络成本；大图片不应成为首页首屏性能瓶颈。
- 交互状态使用 aria-live / focus-visible 等可访问性机制。
- 减少前端重复请求和重复业务规则。
- 核心业务规则继续由服务端唯一执行。

## 四、页面整改顺序

1. 登录 / 注册
2. 首页
3. 上传运单与处理状态
4. 运单详情 / 待定确认
5. 今日运单
6. 线路申请
7. 线路数据
8. 账号设置
9. 历史查询
10. 管理端

每一页完成后必须同时检查：
- 视觉
- 手机触控
- 断网/超时
- 空状态
- 错误状态
- 权限状态
- 返回路径
- 刷新恢复
- 真实 API 链路

## 五、核心业务回归矩阵

### 运单

- 成功 OCR
- OCR 超时
- OCR 空结果
- 提取 0 门店
- 基准库正常匹配
- 格式变化自动匹配且更正数不增加
- 相似门店进入待定
- 待定全部确认
- 新增门店确认
- 重复门店去重
- 同 storeId 冲突保护
- 保存幂等
- 重复确认幂等
- 今日索引同步失败后的 repair

### 线路

- 未绑定用户
- 已绑定用户
- 申请 pending
- approved
- rejected
- 重复申请
- 解除绑定
- 解除后再次申请
- 司机/配送岗位占用
- 同一用户多线路竞争
- dispatchRoute 与 boundRoute 不同
- 临时线路

### 数据资料

- 只读用户
- 维护用户
- 并发版本冲突
- 新增门店
- 编辑名称
- 编辑导航
- 编辑备注
- 调整顺序
- 导入整体替换
- 保存后版本更新

## 六、禁止事项

- 不推倒现有核心架构。
- 不清空 Redis。
- 不使用 FLUSHDB / FLUSHALL。
- 不把真实门店名称写成硬编码例外。
- 不把门店导航/备注并入名称。
- 不在客户端复制核心匹配规则。
- 不通过提高模糊匹配阈值掩盖真实提取问题。
- 不以“代码看起来正确”替代真实业务回归。
- 不在未有部署证据时声称已部署。
