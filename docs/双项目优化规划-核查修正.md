## 2. 双项目优化路线图（分 5 阶段）

### 阶段 0：建立验证护栏（最高优先级，对应审计 P2 测试证据缺失）
- **Web CI**：在 `zhipei-one` 增加 `node --test tests/`，重点跑 `sw-precache.test.mjs`（缓存一致性硬门）与 `appearance-theme-bootstrap.test.mjs`（主题/危险按钮标准）。
- **App CI**：新增"常规分支/PR 提交也跑 Android 构建（不发布 Release）"的 workflow，解决审计 P2"自动构建不覆盖常规提交"——保证下一次提交若破坏 APK 能被发现。
- **本地核查手段**：`scripts/bump_asset_versions.py` 会重写文件（**无 dry-run 模式**，CI 里跑即可；本地跑前先 commit 以便回滚），其"同路径旧哈希不一致"检查可复核缓存一致性；或直接依赖 `sw-precache.test.mjs` 只读断言。
- 产出：可重复的"红/绿"证据，取代"部署成功 = 通过"的错觉。
- **已完成（2026-10-19）**：Web CI 落地并修复转绿——修 Node 20→22（sw-precache 的 `globSync` 需 Node≥22，此前 CI 自该测试入库起连续 10 条全红）、rollup 测试入链、`engines.node>=22`；App 常规构建门禁 `android-build-check.yml` 已建。最新 CI run 全绿（sw-precache 94 断言 + HISTORY_ROLLUP 14/0 + BOOTSTRAP_AGGREGATE 15/0 + 全链）。

### 阶段 1：Web 一致性收口（对应审计 P1，但按核查结果收窄）
- 跑 `sw-precache.test.mjs`：绿 → 审计 P1 缓存不一致不成立（当前主分支已一致）；红 → 按报错修。
- 危险按钮：确认红色为既定标准，**无需改**（已自洽）；仅当产品方正式推翻该标准时才动。
- 域名/会话策略文档：写清"Web 对外域名 `zhipeione.ccwu.cc` 为唯一正式入口；App 应统一指向该域名"，消除"同一 cookie 会话"的跨域误解。

### 阶段 2：认证 / 权限 / 数据安全验收（对应审计第二节第 3 + 第四阶段部分）
按清单用真实运单主线逐项断言（而非只看页面）：
- OCR 失败 / 超时 / 取消 / 重复提交后，运单是否留错误态或重复记录；
- 门店身份、业务编码、别名、线路顺序是否误合并；
- 用户是否仅能访问自己的运单与被授权线路（跨用户隔离）；
- 管理员 / 普通 / 会话过期 / 停用账号权限是否一致；
- 删除运单后，索引（`zp:route:*:waybills:<date>`）、统计、`zp:waybill:*`、回收站是否同步；
- 历史检索触达 `Budget` 资源上限时是否明确报错而非静默漏记；
- OCR/Redis 配置异常时页面是否展示真实原因；
- PWA 是否只缓存静态壳、绝不缓存 `/api/*` 业务数据与登录态。

### 阶段 3：App 生产加固（对应审计第三节）
- **域名统一**：`capacitor.config.json` 的 `server.url` 从 `tianyou-zhipei.pages.dev` 改为 `zhipeione.ccwu.cc`（或反之定唯一正式域名），消除 Cookie 跨域。
- **明文收紧**：`AndroidManifest.xml:12` `usesCleartextTraffic="false"`；`network_security_config.xml` 删除两个 cleartext `domain-config`（代码注释已建议 prod 删除）；保留 https。
- **allowBackup**：结合会话/本地数据敏感性评估，考虑 `false` 或定义明确 backup 规则。
- **常规构建门槛**：PR/分支 push 也跑 build（不 release）。
- **APK 验收**：核对签名证书、比对 `downloads/manifest.json` 记录 size、检查最近一次 Android 构建完整日志（签名与安装未验收前，不得宣称"安装通过"）。

### 阶段 4：业务闭环真机验收
- 真机跑通：登录、拍照上传、返回键、离线恢复、主题同步（注意 `js/ui-unified.js` 已通过 `ZhipeiNative.applyTheme` 回传壳状态栏底色/深浅，`appearance-theme-bootstrap.test.mjs:77-81` 已锁定）。
- 失败/重试路径必验：OCR 失败不伪装成功（OCR 适配层应返回错误）、弱网下离线缓存仅壳不缓存业务数据。

### 阶段 5（可选，源于此前讨论）：历史性能 rollup
- 写入侧维护 `zp:stats:day:/month:/year:<routeId\|ALL>` 汇总键；历史概览/（若做）年度统计改读 rollup，根治"历史越多越慢"。
- **用户已拍板：用户首页显示保持现状不变**（`home-bootstrap.js` 仅返回 dispatchRoute+user），性能改造零触碰首页；预算全花在历史概览页与（若做）管理员年度统计页。
- **已完成（2026-10-19 上线）**：写入侧维护每日汇总键 `zp:route:{routeId}:waybills:{date}:meta={v:1,count,storeCount,totalWeight}`，概览读 meta 小键（O(天数)）+ 索引 SMEMBERS；legacy 缺 meta 批量自愈回填；严格 owner 模式不信 meta、逐日读体按 `createdBy` 过滤且不回写；删除/恢复/确认/保存全路径挂钩；管理员 `diagnostic?action=rebuild-meta` 游标回填。40 天 legacy 概览仅 9 个子请求；`npm run test:node` 全绿，rollup 专项 14/0，已上线（commit `7d0656f4`）。

## 3. 双项目职责边界与协作机制（深化审计第四节）

- **Web（`zhipei-one`）**：页面 · API · OCR · 业务逻辑 · Redis · R2，并负责接收 APK 镜像与更新下载清单。
- **App（`zhipei`）**：Capacitor 壳 · 原生状态栏/返回键 · APK 构建与发布。App 是 Web 的"另一个运行容器"，不是第二套业务实现。
- **唯一版本真值**：git tag `vX.Y.Z`（已落地）→ CI 构建 APK + `sync-download` 自动镜像 APK/`manifest.json`/`version.json` 到 `zhipei-one` 并建同 tag 发行版。人工改版本号环节已消除。
- **域名/会话**：写清唯一正式域名，App 与 Web 同域共享 cookie 会话。
- **发布门槛**：Web 业务回归 + Android 构建/安装检查 = 发布前置条件。
- **红线**：Cloudflare 部署成功 ≠ 业务验收；APK 生成成功 ≠ 安装验收；代码/测试/缓存版本/发布记录/最终状态须对应到具体提交。

## 4. 本项目专有补充（审计未覆盖但重要）

- **`bump_asset_versions.py` 约定**：改任何 CSS/JS 后必须跑（CI 已用 `sw-precache.test.mjs` 强制）。注意该脚本**无 dry-run**，本地跑会写文件，CI 跑即可。
- **SW 行为已论证安全**：`/api/*` 永不缓存；HTML 在线交还浏览器（bfcache，不膨胀历史栈），离线才 SW 兜底；CSS/JS 走 SWR（`?v=` 同 URL 命中即返回）。因此"页面打开慢"的主要风险在**业务 API / 历史宽窗口 SCAN**，不在静态资源（除非 `?v=` 失配，已被测试挡住）。
- **历史性能**：此前已分析"按日懒加载 + rollup"方案；用户首页保持现状即可，无需为性能加统计。

## 5. 结论

- 审计总体方向正确；两条 P1 经核查需修正——缓存一致性**当前主分支已一致**（未复现双版本），危险按钮红色**是测试锁定的标准**（非缺陷）。App 侧域名差异、明文流量（`usesCleartextTraffic=true` + cleartext `domain-config`，代码注释已建议 prod 删除）、`allowBackup=true` 均**确认属实**，是真实加固项。
- **优化优先级**：阶段 0 验证护栏 ＞ 阶段 1 一致性收口 ＞ 阶段 2 权限/数据验收 ＞ 阶段 3 App 加固 ＞ 阶段 4 真机闭环（阶段 5 可选）。
- 全程不清空数据、不改未确认业务阈值、不以静态代码推断生产功能正常、不在缺构建日志与验收结果时宣布完成。
