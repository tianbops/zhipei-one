# 适配One 全新版本架构契约

版本：2026-09-27
状态：正式设计基线
适用：Web / Android / 微信小程序 / 服务端

## 1. 版本定位

本版本是一次独立重建，不是旧版本的继续打补丁。

旧版本仅作为历史资料，提供：
- 已验证业务需求
- 用户实际操作习惯
- OCR失败案例
- 数据模型经验
- 线上故障与回归案例

旧代码、旧页面、旧接口、旧数据结构均不具有继承优先级。若与本契约冲突，以本契约和后续正式设计为准。

## 2. 核心业务链

运单
→ 识别
→ 提取
→ 匹配
→ 去重
→ 规划
→ 校验
→ 确认
→ 当日运单
→ 历史
→ 基准库学习

职责边界：
- OCR：负责“看见什么”
- 提取：负责从OCR结果形成结构化运单数据
- 业务引擎：负责“这是什么”，包括标准化、门店匹配、待定/新增判定、去重
- 规划引擎：负责“今天怎么送”，包括线路顺序与规划结果
- 服务端：唯一业务规则执行者
- 客户端：展示状态、提交用户操作，不复制核心业务规则

## 3. 线路模型

线路是独立系统实体，不属于某一个用户。

用户关系分为：
- boundRouteId：用户负责维护的绑定线路
- routeDuty：driver / delivery
- dispatchRouteId：当天实际调度线路

三者不可混用。

约束：
- 每个用户最多绑定一条维护线路
- 每条线路最多一名司机、一名配送员
- 管理员只能管理系统，不进入配送业务
- 管理员负责创建线路
- 普通业务用户通过申请/审批获得线路维护权限
- 当天调度线路可以与绑定维护线路不同
- 空线路允许存在

## 4. 基准库与门店

门店身份以 storeId 为核心。

门店记录至少包含：
- storeId
- originalOcrName
- standardName
- aliases
- navigation
- routeOrder
- note

匹配优先级：
1. storeId
2. 标准名称
3. 已知别名
4. 规范化名称
5. 无法可靠确认时进入待定/新增

不得为了提高匹配率强制进行不可靠模糊匹配。

OCR格式变化（换行、空格、括号、标点、Ⅱ/II等）不计入“名称更正”。

待定/新增门店只有在用户明确确认后，才允许：
- 写入线路基准库
- 建立正式storeId
- 写入别名/标准名称
- 建立学习数据
- 参与后续自动匹配

## 5. 数据写入原则

客户端不得直接决定最终业务数据。

关键业务写入必须由服务端完成，并具备：
- 权限校验
- 输入校验
- 幂等控制
- 冲突检测
- 原子性要求
- 可追踪错误

禁止通过“默认创建线路”等隐式行为产生正式线路实体。

## 6. 运单唯一性

同一天、同线路下，以下组合相同视为同一业务运单：

日期 + 线路 + 车辆 + 总重量 + 门店集合

重复确认不得产生第二条历史记录；应返回已存在业务结果。

## 7. 历史

历史保留100天。

展示规则：
- 按月份折叠
- 月度合计隐藏小数
- 日期默认折叠
- 日期显示“x笔”
- 进入详情后查看具体运单

历史删除必须经过权限检查，并与业务写入使用一致的并发/锁策略。

## 8. 处理状态

正式处理状态：

IDLE
→ SELECTING
→ OCR_RUNNING
→ TEXT_REVIEW
→ PARSING
→ REVIEW_REQUIRED
→ READY_TO_CONFIRM
→ CONFIRMING
→ COMPLETED

错误状态：

OCR_FAILED
PARSE_FAILED
TIMEOUT
CANCELLED
NETWORK_ERROR
AUTH_EXPIRED

任何成功或失败终态都必须释放前端loading和未完成上传状态。

## 9. 用户界面原则

产品面向手机优先，采用成熟安卓配送/订单类软件的交互思路。

统一规则：
- 页面标题使用“线路”，不使用“路线”
- 用户业务链使用“识别 → 提取 → 匹配 → 去重 → 规划”
- 保存/确定在右，取消在左
- 按钮避免过亮
- 深色、专业、紧凑
- 弹窗、表单、状态框统一视觉规范
- 状态框短内容单行；长内容最多3行并内部滚动
- 不允许状态信息覆盖按钮或造成页面跳动

统计展示：
- 日期
- 门店数 · 总重量
- 原始数 / 更正数 / 合并数
- 新增仅在大于0时显示
- 待定存在时显示
- 最终“总门店”以去重/合并后的结果为准

## 10. 安全底线

- Redis仅允许操作zp:*业务命名空间
- 禁止FLUSHDB
- 密钥只允许存在于Cloudflare Secrets
- 已暴露的Redis token必须视为泄露并轮换
- 管理员清理测试数据必须保留当前管理员身份
- 旧会话必须能够通过sessionVersion失效
- 管理员与配送业务接口必须严格隔离

## 11. 开发与验收规则

每个核心阶段：
1. 设计
2. 实现
3. 静态审计
4. GitHub main提交
5. 等待部署
6. 真实业务回归
7. 发现问题立即定位修复
8. 回归通过后才能进入下一阶段

不得以“代码看起来正确”代替真实回归。

## 12. 阶段顺序

Phase 1：干净代码基线、认证、统一API、基础数据模型
Phase 2：线路与权限
Phase 3：OCR与提取
Phase 4：匹配、待定、新增、去重
Phase 5：规划与保存
Phase 6：今日线路、历史、学习闭环
Phase 7：Web UI、管理端、小程序接口
Phase 8：真实运单全链路回归

本文件是新版本设计总契约。后续实现文件若与本契约冲突，应先修正设计/实现，不通过兼容旧逻辑掩盖冲突。


## 账号准入补充

业务账号采用管理员邀请码准入；邀请码支持使用次数、有效期、启停管理，注册时服务端原子校验并消费。账号注册与线路绑定审核保持分离。


## 13. 运单非门店数据与调度线路补充

运单长期核心运输字段仅保留：
- 运输日期
- 车牌号
- 总重量
- 门店原始顺序

不保留：
- 总数量
- 总体积
- 运单号
- 原始运单图片

驾驶员、配送员不作为OCR运单长期字段保存，人员关系由账号与线路关系确定；运单图片仅用于当前OCR识别，处理结束后释放。

OCR不得因最终不保存某字段而提前过滤可能有价值的门店识别线索。OCR负责尽可能完整识别，提取形成候选信息，全局学习负责门店身份识别，线路数据资料负责当前线路归属与顺序，规划引擎负责最终规划。

运单归属以用户当次调用的线路为准，不根据门店历史归属自动改换线路。全局学习只负责识别门店身份，不负责改变运单线路归属。

调用线路增加“临时线路”：用于加班、临时支援或无固定线路用户。临时线路不是正式线路实体，不创建正式线路数据资料、不参与正式线路绑定；可以使用全局学习识别门店，规划按照运单原始顺序排列。临时线路产生的运单仍保留其当次调用上下文，但不得自动生成或污染正式线路数据资料。
