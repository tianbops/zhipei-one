# 适配One 优化版变更说明

版本：2026-10-02
基线：zhipei-one-main（原架构基线）
范围：**门店匹配引擎重构 + OCR 适配层加固**

---

## 一、本轮解决的核心问题

用户反馈的痛点是**匹配准确率**。经代码审计 + 真实回归测试，定位到根因：

> 原匹配算法使用「字符集合交并比」计算相似度，**对字符顺序完全不敏感**。
> 这在 OCR 场景下极其危险——识别结果一旦出现乱序或错位，会被判定为 100% 相同。

### 实测复现（原算法）

| 识别原文 | 基准库门店 | 原算法得分 | 原判定 | 正确应为 |
|---|---|---|---|---|
| 津天科万城店 | 天津万科城店 | **1.000** | ✅ 自动匹配 | ❌ 完全不同 |
| 店龙华华润万家 | 华润万家龙华店 | **1.000** | ✅ 自动匹配 | ❌ 识别错位噪声 |
| 星巴克深圳湾二店 | 星巴克深圳湾店 | **0.875** | ✅ 自动匹配 | ❌ 可能是另一家门店 |

**后果**：运单会被配送到**错误门店**，且因为得分很高，用户在界面上完全看不出来。

## 二、匹配引擎 v2（`functions/api/waybills/_store-match.js`）

### 2.1 算法重构

由「单一集合相似度」改为「**多信号加权投票 + 硬性守门 + 显式置信差**」：

| 信号 | 权重 | 作用 |
|---|---|---|
| Levenshtein 编辑距离（整体） | 20% | 整体差异度量 |
| 编辑距离（剥离业态后缀后主体） | 22% | 忽略"店/超市/商场"差异 |
| 二元字符组 Jaccard | 16% | 捕捉局部相邻关系 |
| 三元字符组 Jaccard | 14% | 更严格的顺序约束 |
| 最长公共子序列比率 | 20% | **对字序敏感**，抗插入删除 |
| 拼音首字母相似度 | 8% | 容忍同音字识别误差 |

### 2.2 守门规则（拦截危险匹配）

| 规则 | 触发条件 | 处理 |
|---|---|---|
| **乱序拦截** | 字符集合重合 ≥95% 但相邻关系重合 <45% | 直接否决，强制待定 |
| **主体编号差异** | 差异仅来自主体位置数字（1号店/2号店） | 降权至 ≤0.65，强制人工确认 |
| **后缀序号差异** | 差异仅来自末尾序号（梅林店/梅林二店） | 小幅加分，视为同店别称 |
| **歧义保护** | top1 与 top2 分差 < 0.05 | 强制待定，交人工选择 |

### 2.3 阈值调整

| 参数 | 原值 | 新值 | 说明 |
|---|---|---|---|
| 自动匹配阈值 | 0.86 | **0.90** | 提高，宁严勿松 |
| 置信差要求 | 无 | **0.05** | 新增，落实架构契约 |
| 候选下限 | 0.86 | 0.70 | 让更多候选可被人工选择 |

### 2.4 顺带修复的真实 Bug

**业务编码索引遗漏**：基准库门店的 `businessStoreCode` 正式字段未被纳入编码索引，
导致带业务编码的门店无法按编码匹配。原代码同样存在此问题，本轮已修复。

### 5.1 问题

原实现硬编码依赖百度 AI Studio 托管服务（`paddleocr.aistudio-app.com`）。
该服务需要 access token，属于**第三方免费额度**，存在限流、失效、数据出境风险。

### 5.2 结论：保持单通道（2026-10-02 晚修订）

**本项改造已回退。** 经用户确认，项目**不需要自建 OCR**，
`ocr.js` 已还原为原始的 **AI Studio 单通道**实现（`functions/api/waybills/ocr.js`）。

回退原因：

| 原方案 | 问题 |
|---|---|
| 双通道 + 自动降级 | 自建服务需要额外服务器与运维成本，项目不具备条件 |
| 285 行适配层 | 相对原始 64 行，复杂度上升但**生产路径完全未变**（仍走 AI Studio） |
| `docs/selfhost-ocr.md` | 无实际使用场景，已删除 |

**生产配置只需一个环境变量：**

| 变量 | 说明 |
|---|---|
| `PADDLEOCR_ACCESS_TOKEN` | AI Studio 令牌（必填） |
| `PADDLEOCR_BASE_URL` | 托管地址（可选，默认官方地址） |

> 保留的唯一天害增强：返回值增加 `provider:"aistudio"` 字段，
> 供 `process.js` 记录实际使用的 OCR 通道，便于排查。

## 六、前端改进（`js/order_detail.js`）

|---|---|
| `no_candidate` | 基准库中无相近门店 |
| `below_threshold` | 相似度不足，请确认 |
| `ambiguous` | 存在多个相近门店，请选择 |

示例：`建议匹配：华润万家(龙华店)（92%），相似度不足，请确认`

这让用户能**看懂系统为什么没自动匹配**，而不是面对一个无解释的"待确认"。

## 十六、PWA 化：添加到手机桌面（2026-10-02 晚）

### 16.1 为什么先做 PWA 而不是小程序

用户提出"做成微信小程序"，评估后**暂缓**，原因不在技术而在准入门槛：

| 门槛 | 结论 |
|---|---|
| 主体资质 | 微信小程序"快递业与邮政 → 物流"类目需企业/个体工商户；**个人主体仅限工具、展示等类目**，物流类目无法过审 |
| 微信认证 | 企业/个体户 300 元/年（个体户活动价约 30 元/年） |
| 域名备案 | `request` 合法域名**必须 ICP 备案 + HTTPS**；现部署在 Cloudflare Pages，`*.pages.dev` 无法备案，需自有域名 + 备案，周期 1–3 周 |
| 成本 | 首年约 400–600 元起步，与"零成本"约束冲突 |

同时确认了一条利好：**改造量其实很小**——OCR、门店匹配、路线规划 100% 在
Cloudflare Functions 内；`_auth.js:3` 已同时支持 `Authorization: Bearer` 与
Cookie；`process.js` 收 `multipart/form-data`，`wx.uploadFile` 可直接对接；
`process.js:190` 本来就内置非流式分支（不传 `?stream=1` 即可）。
真正需要改的后端只有一处：`login.js` 目前只通过 Set-Cookie 下发 token，
响应体里没有 token 字段，小程序存不了。

> 结论：小程序随时可以做，但先落地 **零成本 PWA** 验证效果。PWA 的差距只有
> 微信入口、原生拍照体验和订阅消息推送三项。

### 16.2 新增文件

| 文件 | 作用 |
|---|---|
| `manifest.json` | 应用名/图标/`standalone`/竖屏，含 2 个快捷方式（上传运单、今日路线） |
| `sw.js` | Service Worker：预缓存 App 壳，离线可用 |
| `offline.html` | 断网兜底页（与全站深色风格一致，带重试按钮） |
| `js/pwa.js` | 仅负责注册 SW，失败静默忽略，不支持时退化为普通网页 |
| `assets/icons/*` | 由现有 `assets/logo.png` 生成：192/512/maskable-512/apple-touch-icon(180) |
| `_headers` | Cloudflare Pages 缓存头：**`sw.js` 必须 no-store**，否则新版本无法下发 |

### 16.3 缓存策略（核心原则：业务数据永不缓存）

| 请求类型 | 策略 |
|---|---|
| `/api/*` | **直接透传，绝不入缓存**（登录态、运单、线路必须实时） |
| 非 GET（登录提交、运单上传） | 不拦截 |
| 页面导航 | network-first，失败回退缓存，最后回退 `offline.html` |
| CSS/JS/图片 | stale-while-revalidate（先秒开，后台静默更新） |

缓存 key 一律用 `pathname` 规整化：登录跳转和刷新常带 `?v=时间戳`，
若按完整 URL 缓存，每次跳转都会产生一份新副本。

预缓存 21 项：App 壳 + 司机高频页（`home.html`、`pages/today.html`）+ 全部 CSS/JS。

### 16.4 两处配套改动（让 PWA 真正可用）

1. **`index.html` 已登录自动跳转**：会话仍有效时直接进 `home.html`（管理员进
   `admin.html`）。否则从桌面图标每次打开都停在登录页，还要再点一次登录——
   那样 PWA 就失去意义了。退出登录后 `/api/me` 返回 401，不会跳转，换账号不受影响。
2. **`pages/account.html` 新增"添加到手机桌面"卡片**：Android/Chrome 走
   `beforeinstallprompt` 显示按钮；iOS Safari 不支持该事件，改为给出
   "分享 → 添加到主屏幕"的手动步骤；**已安装（standalone）时整块隐藏**。
   全部复用现有 `.page2-card` / `.page2-soft` / `.page2-primary`，零新增 CSS。

### 16.5 部署注意

- PWA 要求 HTTPS，Cloudflare Pages 默认满足。
- **`_headers` 必须一起部署**：Cloudflare 默认会缓存 `sw.js`，若被 CDN 缓存住，
  新版本 SW 永远下发不到客户端，用户会一直用旧缓存。
- 更新 SW 时改 `sw.js` 里的 `VERSION` 常量即可，旧缓存会在 activate 阶段自动清理。

## 十七、旧内核兼容加固（2026-10-03 凌晨）

确认司机**主要用微信内置浏览器打开**（微信里点链接），因此 PWA 的"添加到桌面"
在安卓微信上无法安装——这层对当前使用场景基本无效，但保留它成本为零且无害
（哪天改用系统浏览器就生效）。真正该做的是**针对微信 X5 内核的兼容加固**。

安卓微信内置浏览器基于版本偏旧的 X5/Chromium 内核，以下现代 CSS 会被**整条声明
丢弃**（不是部分降级），从而造成布局塌陷：

| 特性 | 失效后果 | 本项目的用法 |
|---|---|---|
| `dvh` 视口单位 | `height:100dvh` 丢失 → **运单详情页高度塌陷**；`min-height` 丢失 → 深色背景铺不满 | 11 处（含 1 处危险的 `height:100dvh`） |
| `inset` 简写 | 弹窗/遮罩定位丢失 → 覆盖错乱 | 5 处 |
| `backdrop-filter` | 仅影响毛玻璃观感，无功能影响；缺 `-webkit-` 前缀安卓不生效 | history.css 2 处 |

### 17.1 加固方式（渐进增强，不支持的浏览器自动降级）

```css
/* 加固前 */
.order-shell{height:100dvh}

/* 加固后 */
.order-shell{height:100vh;height:100dvh}
```

- **`dvh`**：在每条含 `dvh` 的声明前补一条同名 `vh` 版本。支持 `dvh` 的浏览器
  用后者，不支持的用前者，不会塌陷。
- **`inset`**：补 `top/right/bottom/left` 四值兜底，再跟原 `inset`（含
  `!important` 版本同样处理）。
- **`backdrop-filter`**：仅给**整个文件都没有 `-webkit-` 前缀的**补前缀
  （`ui-unified.css` 作者已写前缀，保持原样不重复添加）。

涉及：`app.css` / `business-pages.css` / `data.css` / `home.css` /
`order_detail.css` / `history.css` / `ui-unified.css`。
